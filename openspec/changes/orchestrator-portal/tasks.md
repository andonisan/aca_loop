## 3. Read-model views

- [x] 3.1 Queue + executions panel per stack: approximate message count and running/recent ACA job executions via managed identity (Azure SDK), with per-source cache TTLs; a failing source renders that panel unavailable without breaking the page — `QueueDepthSource` (approximate message count) and `PodExecutionsSource` (ACA job executions, running first since ACA guarantees no ordering) behind `IPanelReader`, rendered on a new per-stack dashboard at `/stacks/{id}`. Both cached on their own TTL and degrading independently: a broken source renders `PanelUnavailable` in its own card while the rest of the page stands. `PodExecution` carries the already-parsed `PodExecutionState` rather than a raw string — that enum documents itself as parsed at the boundary, and this source *is* the boundary — plus the raw Azure status for the badge's hover title so an `Unknown` is diagnosable. **Not verified live: no stack is deployed, so neither source has returned a real row**
- [x] 3.2 Run-history view per stack: cross-workspace Azure Monitor Query using the task-1.3 KQL (outcomes, durations, success rate over a selectable window, failure log-tail pointer); label history depth as workspace retention — `RunHistorySource` over the reference KQL already documented on `LifecycleEvents`, including its `SchemaVersion` pin, with a selectable 1/7/30-day window. **Two queries, deliberately:** the row list is capped for display, so counting it would report the most recent N runs' success rate as the window's. The aggregate is its own `summarize`. `SuccessRate` is null rather than zero when nothing ran — zero reads as "everything failed". The window is part of the source's cache identity, so a 7-day view never serves its rows to a 24-hour one. History depth is labelled as workspace retention in the UI. **KQL shape was previously validated against a live workspace (see `LifecycleEvents`); these SDK calls have not been**
- [x] 3.3 Gated-items view per stack: list items currently in mapped states via the vendor adapter modules using dedicated read-scoped credentials; unmapped states never appear — **blocked on a design gap, not on effort.** `IBacklogAdapter` only exposes `ReadItemStateAsync(project, repo, itemId)`: the state of one item whose id you already have. This task needs the inverse — enumerate the items currently in a mapped state — and no adapter has any list/search/query operation. There is a second, sharper problem: the spec requires dedicated read-scoped credentials, but the adapters are constructed from the `Vendors:*` options carrying write-capable secrets, so reusing the adapter type in the portal would let someone wire the agent's write credentials in with nothing in the type system to stop them. Needs a separate read-only contract (a per-vendor `IBacklogReader` constructed with read-scoped credentials), which makes "the portal cannot use write credentials" a compile-time fact the same way the tracker/code-host split did. That is a design decision for design.md, not something to invent inside a task — **done, after resolving the design gap it was blocked on.** `IBacklogReader` (design D9) is a read-only contract per vendor, taking a read-scoped credential it cannot escalate; all four vendors implement it. `GatedItemsSource` resolves gate states from that stack's own mapping through the same `MappingLoader` its receiver uses, so the portal cannot display a different set of gates than the one that actually dispatches, and unmapped states never appear. **A second design fault surfaced while wiring it:** the readers as first written took per-vendor options and a fixed `HttpClient.BaseAddress`, which suits the receiver (one target per deployment) but not the portal (many stacks, and two can be on different GitLab or Jira instances). So `StackVendorCoordinates` gained `BaseUrl` and Jira's per-stack `Deployment`, and readers are now built per stack by `BacklogReaderFactory` rather than registered as singletons. The gate table shows the raw vendor state rather than a status treatment: those are the client's own gate names and mapping them onto a fixed palette would assert a meaning this portal does not have. **Unverified live** like every other vendor path here
- [x] 3.4 Cross-stack overview page: one row per registered stack (queue depth, running pods, last outcome, success rate), capped/paginated rollup queries — `/overview`, one row per registered stack (queue, running pods, last outcome, success rate), fanned out across stacks and sources concurrently. Rows for an unreachable stack render `Unreadable` per cell rather than being dropped: a stack silently missing from a rollup is the worst failure mode here, and "0 queued" must not look like "we could not ask" when only the first is safe to act on. Capped by the same per-source limits as the per-stack view, and it shares cache entries with it, so opening both costs one set of reads
