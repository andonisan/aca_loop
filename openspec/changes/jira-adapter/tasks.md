## 1. Tracker/code-host separation (all vendors, mechanical)

- [x] 1.2 Add `CodeHost` + `CodeRepo` to `CanonicalMessage`, documenting on both records that the tracker coordinates identify the item and the code-host coordinates identify the repository — **corrected during implementation: the fields belong on `CanonicalMessage` only, not on `CanonicalEvent` as originally written.** An adapter's `ParseEvent` knows its own tracker but not the target's configured code host (that is mapping config, resolved by Dispatch *after* parsing), so putting them on the event would force a tracker-only adapter like Jira to invent values it cannot know — the same "interface lies" smell D6 rejects. `CanonicalEvent` instead documents that `Repo` is empty for a non-repo-anchored tracker. Spec updated to match (`backlog-abstraction`: the requirement is now "code-host coordinates on the canonical queue message", with a scenario pinning that adapters do not supply them)
- [x] 1.3 Re-declare the GitHub, GitLab, and Azure DevOps modules as implementing both interfaces; their behavior must not change. Verify `ArchTests` and the MOD analyzers stay green — cross-module access remains contracts-only — all three adapters now declare `: IBacklogAdapter, ICodeHostAdapter`. **DI needed restructuring:** `AddHttpClient<IVendorAdapter, TAdapter>` cannot register one instance under two interfaces, so each module now registers the concrete adapter via `AddHttpClient<TAdapter>` and forwards both contracts to it. Forwards are `AddTransient`, not `AddSingleton` — `AddHttpClient` registers its client as transient, so a singleton forward would capture a transient `HttpClient` (a captive dependency). Build clean at 0 warnings (warnings-as-errors), all 5 ArchTests green
- [x] 1.4 Move `ExecutionService`'s vendor `switch` for CLI token env vars onto `ICodeHostAdapter`, and **add the missing Azure DevOps case** found while tracing the seam (ADO targets currently get git credentials via `CloneUrl` and no CLI token at all) — the switch is gone; each code host owns `GetCliEnvironment(credentials)`. GitHub contributes `GH_TOKEN`+`GITHUB_TOKEN`, GitLab `GITLAB_TOKEN`, and Azure DevOps `AZURE_DEVOPS_EXT_PAT` — the variable the Azure CLI devops extension reads, which ADO runs previously never received at all
- [x] 1.5 Update `ExecutionService` to resolve two adapters per message — tracker for gate re-validation and the failure contract, code host for clone credentials and environment — and confirm the existing Execution unit tests still pass against the two-adapter resolution — all 101 pre-existing tests pass unchanged. **One behavioral decision this task forced:** an unregistered *code host* takes the failure contract (transition + comment via the tracker) rather than the poison path used for an unregistered *tracker*. Rationale: it is the same class of mapping/version-skew bug as an unknown runtime, which already fails rather than poisons, and unlike the unknown-tracker case the tracker adapter is available to write the reason onto the item. Added 2 tests for the new paths (unregistered code host → failure contract with no command run; CLI environment sourced from the code host, not the tracker), taking Execution from 16 to 18

## 2. Mapping schema: code-host coordinates

- [x] 2.1 Extend `MappingFile`/`MappingFileTarget` with `codeHost` and `codeRepo`, and `MappingConfig`/`MappingLoader` to default `codeHost` to `vendor` and `codeRepo` to `repo` when absent — done, plus two validation rules the defaults forced: `repo` alone is no longer required (it is now "at least one of repo/project", since a project-scoped tracker has no repo), and a target whose `codeRepo` is still empty after defaulting is rejected because there would be nothing to clone. `Vendor.Jira` was added to the enum here rather than in group 3: the schema cannot express or validate a split target without it. The enum value is documented as adapter-less for now — `/webhooks/jira` is unroutable and a Jira message would find no adapter
- [x] 2.2 Add startup validation that each target's resolved `codeHost` maps to a registered `ICodeHostAdapter`, failing fast with the offending target named — same fail-fast path as every other mapping violation — **could not go in `DispatchModule.Add` with the rest of mapping validation:** adapters are registered by factory, so their `Vendor` is unknowable until the container exists. It runs in `DispatchModule.InitializeAsync` instead, which the Receiver awaits before `app.Run()`, so a violation still refuses traffic. `MappingConfig` is now registered in DI so the initializer can read it. The case this catches today is not Jira but a **disabled vendor**: a target naming `codeHost: GitLab` in a deployment where `enable_gitlab` is false and the module was never composed. 3 tests
- [x] 2.3 Extend `MappingProvider.TryResolve` so a non-repo-anchored tracker matches on its project coordinate rather than requiring a repo match, without changing resolution for the three repo-anchored vendors — `TargetMapping.Matches` branches on an empty `Repo`. **`IMappingProvider.TryResolve`'s signature changed** as a consequence: it now yields a `ResolvedTargetState(Target, State)` rather than a bare `StateMapping`, because the code-host coordinates belong to the *target* and `WebhookUseCase` needs both halves. Done now rather than later since the Portal will consume the same interface. A test pins that a target's `codeRepo` never participates in matching — otherwise a GitHub-shaped event could resolve a Jira target
- [x] 2.4 Prove no migration is needed: load the existing `src/root/Orchestrator.Receiver/mapping.yaml` and the portal's bundled `mappings/dsconnect-dev.mapping.yaml` unchanged and assert identical resolution behavior (design.md Migration Plan step 4 — a task, not an assumption) — a test loads the actually-shipped `mapping.yaml` (located by walking up to `orchestrator.slnx`, not a brittle relative path) and asserts every target resolves `CodeHost == Vendor` and `CodeRepo == Repo`. **Deliberately asserts on the parsed result, not on the file text:** an earlier draft asserted the file contains no `codeHost` string, which would have falsely failed once task 5.2 adds a commented Jira example. ## 3. Jira adapter

- [x] 3.1 Create `src/modules/Jira/Orchestrator.Modules.Jira` (self-registering `IModule`, `Vendor.Jira`) implementing **only** `IBacklogAdapter`; add `"jira"` to `WebhookUseCase.TryParseVendor` — `JiraModule` forwards `IBacklogAdapter` only, with no `ICodeHostAdapter` registration, which is what makes "Jira cannot be a code host" true at compile time *and* at startup (the group-2 registration check has nothing to find). Wired into `.slnx` alongside a new `Orchestrator.Modules.Jira.UnitTests`
- [x] 3.2 Implement `VerifyWebhook`: HMAC over the raw body against the configured secret, fixed-time compare, `X-Hub-Signature` parsed in its `method=signature` form with unsupported methods rejected, and a missing header rejected rather than treated as unconfigured (design.md D2) — sha256 and sha1 are accepted, anything else is rejected rather than verified with a default algorithm, since Atlassian documents the method may change. 5 tests
- [x] 3.3 Implement `ParseEvent`: accept only `jira:issue_updated`, require a `changelog.items[]` entry with `field == "status"`, take `toString` as `native_state`, the issue **key** as `ItemId` (design.md D7), and the Jira project key as the project coordinate — accepts only `webhookEvent == "jira:issue_updated"` (Jira carries the event type in the **body**, not a header, unlike all three other vendors), requires a `changelog.items[]` entry with `field == "status"`, and emits `Repo: string.Empty` since a Jira issue belongs to a project
- [x] 3.4 Implement `IsAutomationActor` comparing the payload actor's account identifier (not display name) against the configured orchestrator account — compares `user.accountId`, falling back to `user.name` because Data Center has no account ids. Never the display name: mutable and not unique
- [x] 3.5 Implement `ReadItemStateAsync` reading the live status by issue key, for gate re-validation — `GET issue/{key}?fields=status` → `fields.status.name`
- [x] 3.6 Implement `TransitionStateAsync` via transition discovery: GET the transitions available from the current status, match the target status name, POST the transition id. Never attempt a status field edit (design.md D5) — `GET issue/{key}/transitions` → match on `to.name` → `POST {transition:{id}}`. A test asserts the POST body contains the matched id and **no** `status` field, pinning that the issue-edit path is never used
- [x] 3.7 Implement the unreachable-failure-state path: when no transition to the configured `onFailureState` exists, still post the failure-context comment, still record a failed outcome, leave status unchanged, and report the original run failure as the cause rather than the transition failure — **the real fix landed in `ExecutionService.FailAsync`, not the adapter.** The transition and the comment shared one `try` with the transition *first*, so a throwing transition skipped the comment entirely and left the item with neither a new state nor an explanation. Now the comment is posted first, and the transition is wrapped in its own `catch` that logs `FailureTransitionUnavailable` (new event id 1308) as context — the outcome was already emitted before either call, so the original run failure stays the reported cause. The adapter throws with the reachable status names listed, because "no transition reaches X" is only actionable alongside what does
- [x] 3.8 Implement `PostCommentAsync` against the comment endpoint for the configured deployment: Cloud → v3 with a minimal ADF wrapper (`doc → paragraph → text`); Data Center → v2 with a plain-text/wiki-markup body (design.md D11 — ADF does not exist on Data Center) — Cloud → v3 with a minimal ADF wrapper; Data Center → v2 with a plain body. ADF gets **one paragraph per line**: ADF text nodes have no notion of a newline, so a multi-line log tail would otherwise collapse onto one line
- [x] 3.9 Add `JiraOptions` with a single `Deployment: Cloud | DataCenter` setting driving API version, comment format, and auth scheme as one coupled choice (design.md D11), plus base URL, account/email, API or personal access token, webhook secret, and bot account id. The three coupled values MUST NOT be independently settable — `JiraOptions` with one `Deployment` setting deriving `ApiVersion`, comment format, and auth scheme (Basic on Cloud, Bearer on Data Center). Two extra knobs were added for testability and ops: `MaxRetries` and `RetryBaseDelayMilliseconds`, so the retry-exhaustion tests do not spend ~15 real seconds proving the policy
- [x] 3.10 Implement outbound resilience per design.md D12: explicit timeout and `CancellationToken` on every call, `Retry-After`-aware retry with exponential backoff and jitter, bounded attempts, and — critically — exhausted retries on the failure path still recording an outcome — all four call sites funnel through one `SendAsync` so the policy cannot be forgotten on one of them. Honors `Retry-After` (delta and HTTP-date), exponential backoff with jitter otherwise, retries 429 and 5xx only, and a 30s `HttpClient.Timeout` set in the module so a hung Jira cannot hold an agent replica open until the job watchdog fires. A test pins that a 404 is *not* retried
- [x] 3.11 Add `Orchestrator.Modules.Jira.UnitTests` covering: signature accept/reject/missing-header/unsupported-method; status-change parse; non-status changelog, non-`issue_updated`, and missing-changelog drops; automation-actor filtering; transition selection; the unreachable-failure-transition path; both deployment variants of comment posting; and retry-exhaustion during the failure path. Note that the GitHub adapter still has no unit test project — do not repeat that gap here — 21 tests in `Orchestrator.Modules.Jira.UnitTests` plus 1 in Execution for 3.7's reordering. **A bug in my own test helper surfaced here:** it reused one `HttpResponseMessage` across retries, but the adapter disposes each response, so the second attempt failed on a disposed content stream instead of exercising the retry. The handler now takes response *factories*
