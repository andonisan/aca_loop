## 2. Shell and reference consumer

- [x] 2.1 Rebuild `MainLayout.razor` as the Atlas app shell — `.app-shell` grid, `.sidebar` (brand, registry-driven `.nav-group`, `.user-card`), `.topbar`, `.page` well. The `@Body` gate and its comment carry over verbatim. **One authorization change was required rather than avoided, and it tightens rather than relaxes:** the sidebar renders client display names, which is stack data, so the stack nav sits behind its own `PortalPolicies.Read` gate. Rendering it in the always-visible chrome would have leaked the client list to any authenticated tenant user — precisely what portal-auth's "no stack data" scenario forbids. The `.user-card` deliberately stays *outside* that gate: it shows the operator their own identity and role, never stack data, and a role-less user needs to see which account they are signed in as to act on the notice.

Reason: `Routes.razor` focuses `h1` after every navigation, so a layout-owned title would have silently broken focus management on every page at once; sections keep the heading in the page's render tree while rendering it in the topbar.

## 3. Domain semantics

- [x] 3.1 Implement the state→treatment mapping (design D4) — `Presentation/StatusTreatment.cs` with `ForOutcome` (enum and wire-string overloads), `ForExecution`, `ForQueueDepth`, plus `Presentation/RunOutcome.cs` holding the `RunOutcome`/`PodExecutionState` enums and the boundary parser. Three decisions beyond the task text:
  (a) **The treatment carries its label, not just a CSS class.** A helper returning a bare class name lets a caller satisfy the type while rendering an empty coloured pill, which is exactly what the "never colour alone" requirement forbids. `StatusBadge(CssClass, Label)` makes the accessible rendering the convenient one.
  (b) **Wire strings are parsed into an enum at the boundary rather than passed through.** An unrecognised outcome must be *visible*; a string flows through a mapping and out as "whatever the fallback is", whereas an explicit `Unknown` member forces every consumer to have a position on schema skew. Unknown renders `orange` / "unknown outcome" — deliberately not `neutral`, so a skewed stack cannot pass for a quiet one.
  (c) **Added `StatusBadgeView.razor`** so the dot-plus-label markup cannot be forgotten and pages have no reason to touch a colour class directly. This is one component ahead of the "three callers" rule in the proposal, justified by the accessibility requirement rather than by reuse.
  `wip-refused` → `neutral` (design D4 left it unstated): backpressure working as designed should be visible without competing with real problems for attention.
- [x] 3.2 Unit-test the mapping — 24 tests in `StatusTreatment_Should_Constraint`. The load-bearing one is `EveryEmittableOutcome_Should_HaveItsOwnTreatment`, which drives off `LifecycleOutcomes.All` and asserts no outcome falls through to the unknown-skew treatment. **Verified by mutation:** adding a sixth outcome (`cancelled`) to the shared contract without a mapping fails with `'cancelled' falls through to the unknown-skew treatment`; reverting passes. `stale-gate` ≠ `failed` and `poison` ≠ `failed` are pinned as named tests with the reasoning in their doc comments, so both have to be argued with rather than quietly reverted. Full suite: 95 tests passing across 7 projects (was 71).
- [x] 3.3 **Deliberate scope addition, found while writing 3.2:** added `LifecycleOutcomes.All` to `shared/Orchestrator.Constants/LifecycleEvents.cs`. The class doc already called the outcomes "a closed set", but nothing could verify that — reflection over the class cannot tell an outcome constant from the two log-pointer constants sitting beside it, so any coverage test would have needed a hand-maintained exclusion list, i.e. the very drift it was meant to catch. Three lines, additive, and it makes an existing claim checkable. Note this touches shared constants, which the proposal's impact section did not anticipate.

Blocked on `orchestrator-portal` task 3.1 (queue read model); until then `ForQueueDepth` takes them as required parameters rather than hard-coding placeholders, and rejects an inverted pair (which would silently disable the danger band) instead of normalising it.

## 4. Extension layer and verification

- [ ] 4.1 Add `wwwroot/css/portal.css` for components Atlas has no equivalent of — run timeline, log-tail viewer, gate-state strip — built from tokens only. Create it when the first 3.x page needs it, not speculatively.
- [x] 4.2 Contrast audit — computed WCAG 2.1 ratios for 28 pairs × 2 themes by converting the OKLCH tokens through OKLab to linear sRGB. Script and full results recorded in `contrast-audit.py` / `contrast-audit.txt` next to this file, per "record rather than assert". **D8's prediction was correct: 10 pairs were below AA.** Fixes, each marked as a divergence at its rule:
  - `--fg-muted` dark 60% → 62% (was 4.17:1 on `--surface-3`, 4.49:1 on `--surface-2` — the 11px table headers).
  - `--info` light 52% → 51.5% (4.49:1 on `--info-soft`; missed by 0.01).
  - `--brand-on` dark `#fff` → `oklch(13% .02 258)` (white on the lightened dark brand was **3.97:1 on the primary button** — the worst finding, and the most-clicked control). Darkening `--brand` instead would have fixed the button and broken `--brand`-as-text, which passes at 4.73/5.06; `--brand-on` exists precisely to absorb this.
  - **`--fg-subtle` could not be fixed by lightness** — reaching AA requires L=62% in dark, identical to `--fg-muted`, collapsing the four-step ramp to three. So it is now documented as **decorative-only** (separators, ellipses, which WCAG exempts), and its two real-text uses moved to `--fg-muted`: `.sidebar-section-title` (11px) and `.tabs .tab .mono` (a count). This is a usage decision, not a value change, and it is the one finding that changes how the ramp must be used.
  Result: both themes clear AA for every text pair at its rendered size.
- [x] 4.3 Keyboard pass — found and fixed one real violation of the spec's "a rule that removes a default outline MUST supply a replacement": `.search-input` set `outline: none` with no focus treatment at all, leaving the search field with no keyboard indicator. The ring now goes on `.search-box:focus-within`, since the input has no border of its own. Also added a shared `:focus-visible` rule for nine primitives that carried none and were relying on the UA default (nav items, tabs, subtabs, filter chips, pager, segmented, breadcrumb links, user-card action, checkbox) — the default ring sits badly on the brand-tinted active states and varies per browser. Tab order verified against the real rendered page: 3 focusable elements, no `tabindex` anywhere (so DOM order *is* tab order), order follows reading order, no `role="button"` needing key handlers, and all three have explicit focus rules.
- [x] 4.4 Theme verification — exercised in a real browser against the actual rendered page, reading computed custom properties. On an OS set to dark: no attribute → dark ✓; `data-theme="light"` → light ✓ (the case that fails if the `:not([data-theme=light])` specificity is wrong); `data-theme="dark"` → dark ✓. **Not verified: light OS with no attribute** — the browser's colour-scheme emulation did not reach the page (`prefers-color-scheme` still reported dark), so that fourth case rests on the cascade rather than on evidence. It is the least risky of the four (no attribute and no dark media match leaves only `:root`).
  **This task caught a real bug rather than confirming one.** The first browser read reported the *old* `--fg-muted` and `--brand-on`, because the 4.2 fixes had landed only in the `[data-theme=dark]` block and not in the duplicated `prefers-color-scheme` copy — the exact hazard design D5 warns about, walked into within the hour. Comments were not enough, so:
