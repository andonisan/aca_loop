## 2. Mapping configuration (state-action-config)

- [x] 2.1 Define the mapping YAML schema: `targets[] → {vendor, project/repo, states[] → {native_state, action, runtime, on_success_state, on_failure_state}}` with JSON-schema validation — implemented as `MappingFile`/`MappingFileTarget`/`MappingFileState` (YamlDotNet, camelCase) validated by hand-written structural checks (`MappingLoader`) rather than a JSON-Schema library: the schema is small enough that this gives the same fail-fast guarantee with one fewer dependency (documented on `MappingLoader`); `on_success_state` is parsed and carried in the validated config but not yet consumed by any behavior (no vendor needs an infra-driven success write-back today — GitHub's is owned by the repo's own command, design.md D5)
- [x] 2.2 Load and validate the mapping at receiver startup; fail fast (unhealthy, no traffic) on schema violations — `DispatchModule.Add` loads+validates eagerly (before `builder.Build()`); an invalid mapping throws and the process never reaches `app.Run()`, verified live: valid `mapping.yaml` starts cleanly, and hand-tested invalid variants (missing `action`, unknown vendor, unknown runtime, empty `targets`) each throw with every violation listed
- [x] 2.3 Replace the receiver's hardcoded gate-label filter with mapping lookup (unknown target or unmapped state → drop) — `WebhookUseCase` now calls `IMappingProvider.TryResolve`; verified live end-to-end with a real HMAC-signed GitHub webhook against the sample `mapping.yaml` (see 2.5)
- [x] 2.4 Replace the agent's hardcoded label→command logic with mapping-driven action/runtime resolution and mapping-aware gate re-validation (stale gate → exit 0, delete message) — action/runtime resolution already lived in Dispatch since task 1.4 (forward-leaning choice made then); this task's remaining piece was the failure-transition target: `CanonicalMessage` gained `OnFailureState` (resolved by Dispatch from the mapping), and `ExecutionOptions.BlockedState` was removed — Agent no longer has any hardcoded or configured state literal, only what Dispatch puts on the message. Gate re-validation itself (`ReadItemStateAsync` vs `message.State`) needs no mapping lookup — it's a live vendor-state comparison, unchanged since 1.4
- [x] 2.5 Ship a mapping file reproducing v1's ds-connect configuration (two gates, `/ds:propose` + `/ds:implement`, blocked-on-failure) and verify end to end — `src/root/Orchestrator.Receiver/mapping.yaml`; verified live: started the Receiver with this file, POSTed a real HMAC-signed `issues`/`labeled` webhook for `status:ready-for-proposal` on the mapped repo, and confirmed it was parsed, passed the automation-actor filter, and resolved through to the enqueue call (traced via the exception stack — it failed only on queue connectivity, which is expected with no queue backend configured in that ad-hoc run); 8 new unit tests in `Orchestrator.Modules.Dispatch.UnitTests` cover resolution, case-insensitive repo matching, unmapped state/target, and every validation failure mode

## 3. Runtime selection hardening (agent-runtime-selection)
