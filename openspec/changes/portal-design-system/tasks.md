## 2. Shell and reference consumer

- [x] 2.1 Rebuild `MainLayout.razor` as the Atlas app shell — `.app-shell` grid, `.sidebar` (brand, registry-driven `.nav-group`, `.user-card`), `.topbar`, `.page` well. The `@Body` gate and its comment carry over verbatim. **One authorization change was required rather than avoided, and it tightens rather than relaxes:** the sidebar renders client display names, which is stack data, so the stack nav sits behind its own `PortalPolicies.Read` gate. Rendering it in the always-visible chrome would have leaked the client list to any authenticated tenant user — precisely what portal-auth's "no stack data" scenario forbids. The `.user-card` deliberately stays *outside* that gate: it shows the operator their own identity and role, never stack data, and a role-less user needs to see which account they are signed in as to act on the notice.
  Title/breadcrumbs are provided by pages through `SectionOutlet`/`SectionContent` (new `PortalSections`) rather than owned by the layout. Reason: `Routes.razor` focuses `h1` after every navigation, so a layout-owned title would have silently broken focus management on every page at once; sections keep the heading in the page's render tree while rendering it in the topbar.
- [x] 2.2 Restyle `Home.razor` as the reference consumer — `.card` + `.card-head` wrapping a `.dtable`, two-line `.cell-primary`/`.cell-secondary` stack cell, every Azure coordinate `.mono`, count as a `.count-pill` in the topbar, an `.empty` state for the (currently unreachable) zero-stack case, and the tasks-3.x caveat as a `.banner info`. Commented as the pattern source the 3.x pages copy.
- [x] 2.3 Restyle `NoRoleNotice.razor` — `.banner` for the "you hold no role" statement, `.card` + `.dl` for the two roles as badges. Keeps its own `h1` in the page well rather than using the topbar section, since it replaces a page rather than being one, and `Routes.razor` still finds an `h1` to focus.
- [x] 2.4 Sidebar nav driven by `StackRegistry` — one `NavLink.nav-item` per registered stack, so adding a stack to `stacks.yaml` needs no markup change. Links target `stacks/{id}`, a route that does not exist yet (arrives with 3.x).
- [x] 2.5 **Strengthened the no-stack-data test (gap found while writing 2.1, not in the original plan).** `AUserWithNoPortalRole_Should_BeToldWhichRolesToAskFor` asserted only `ShouldNotContain("dsconnect-dev")` — the stack *id*. The sidebar renders the *display name*, and `"ds-connect (dev)"` does not contain the string `"dsconnect-dev"`, so ungated client names in the chrome would have passed the test while leaking. ## 3. Domain semantics

- [x] 3.1 Implement the state→treatment mapping (design D4) — `Presentation/StatusTreatment.cs` with `ForOutcome` (enum and wire-string overloads), `ForExecution`, `ForQueueDepth`, plus `Presentation/RunOutcome.cs` holding the `RunOutcome`/`PodExecutionState` enums and the boundary parser. Three decisions beyond the task text:
  (a) **The treatment carries its label, not just a CSS class.** A helper returning a bare class name lets a caller satisfy the type while rendering an empty coloured pill, which is exactly what the "never colour alone" requirement forbids. `StatusBadge(CssClass, Label)` makes the accessible rendering the convenient one.
  (b) **Wire strings are parsed into an enum at the boundary rather than passed through.** An unrecognised outcome must be *visible*; a string flows through a mapping and out as "whatever the fallback is", whereas an explicit `Unknown` member forces every consumer to have a position on schema skew. Unknown renders `orange` / "unknown outcome" — deliberately not `neutral`, so a skewed stack cannot pass for a quiet one.
  (c) **Added `StatusBadgeView.razor`** so the dot-plus-label markup cannot be forgotten and pages have no reason to touch a colour class directly. This is one component ahead of the "three callers" rule in the proposal, justified by the accessibility requirement rather than by reuse.
  `wip-refused` → `neutral` (design D4 left it unstated): backpressure working as designed should be visible without competing with real problems for attention.
- [x] 3.2 Unit-test the mapping — 24 tests in `StatusTreatment_Should_Constraint`. The load-bearing one is `EveryEmittableOutcome_Should_HaveItsOwnTreatment`, which drives off `LifecycleOutcomes.All` and asserts no outcome falls through to the unknown-skew treatment. **Verified by mutation:** adding a sixth outcome (`cancelled`) to the shared contract without a mapping fails with `'cancelled' falls through to the unknown-skew treatment`; reverting passes. `stale-gate` ≠ `failed` and `poison` ≠ `failed` are pinned as named tests with the reasoning in their doc comments, so both have to be argued with rather than quietly reverted. Full suite: 95 tests passing across 7 projects (was 71).
- [x] 3.3 **Deliberate scope addition, found while writing 3.2:** added `LifecycleOutcomes.All` to `shared/Orchestrator.Constants/LifecycleEvents.cs`. The class doc already called the outcomes "a closed set", but nothing could verify that — reflection over the class cannot tell an outcome constant from the two log-pointer constants sitting beside it, so any coverage test would have needed a hand-maintained exclusion list, i.e. the very drift it was meant to catch. Three lines, additive, and it makes an existing claim checkable. Note this touches shared constants, which the proposal's impact section did not anticipate.
- [ ] 3.4 Resolve the queue-depth `warn`/`danger` thresholds against the stack's actual KEDA scale rule — design D4 states the intent but the numbers come from the stack configuration. Blocked on `orchestrator-portal` task 3.1 (queue read model); until then `ForQueueDepth` takes them as required parameters rather than hard-coding placeholders, and rejects an inverted pair (which would silently disable the danger band) instead of normalising it.
- [ ] 3.5 The mapping has **no production caller yet** — its only exercise is its tests, because no page renders status until `orchestrator-portal` tasks 3.x land. Expected given the sequencing (the system lands before the pages that consume it), but it means the wire-string overload has not yet met a real Log Analytics row. Close this when the first read-model page renders an outcome.
